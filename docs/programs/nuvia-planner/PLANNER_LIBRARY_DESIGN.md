# 플래너 라이브러리 설계 규칙

기준일: 2026-10-23. 적용 범위는 필굿 공통규칙의 NUVIA PLANNER 전용 확장이다. 사용자 승인 방향은 기본 라이브러리 우선 사용, 필요한 경우만 AI 생성, 검토 후 공용 축적이다. 이 패키지는 설계·대표 카드 데이터이며 실행 앱 패치가 아니다.

확장판 수량·원본 목록·연결 범위는 [최신 인계서](LIBRARY_EXPANSION_HANDOFF.md)를 따른다. 아래의 6개 맥락 및 12개 원본 설명은 수정하지 않은 v1 기준선이다. 확장판은 성인 311개 직무 ID와 청소년 26개 미리보기 진로를 모두 **초안 연결**했으며, 검토된 운영 매핑으로 승격하지 않았다.

## 1. 두 활동과 하나의 작업대

1. **일상 적용형**: 사용자가 실제 할 일을 선택하고 행동 연습 하나를 붙인다. 실제 수행 여부는 사용자가 확인한다.
2. **직무 상황형**: 가상의 상황에서 사실 확인·선택·이유·조정을 연습한다. 모의 활동으로 표시한다.

두 종류 모두 기존 작업대, 시간 설정, 실행·일시정지·복귀·끝내기·과제 완료 확인을 재사용한다. 새 타이머나 별도 플래너를 만들지 않는다. 카드 추가 시 분야·시간·날짜를 확인하고 작업대에 올린다. 기존 과제에 붙일 때 과제를 복제하지 않는다.

사용 흐름: 직무/진로 선택 → 연습 행동 선택 → 일상 할 일 연결 또는 상황카드 선택 → 도움 방식 확인 → 실행 → 짧은 돌아보기 → 개인 로드맵 확인.

현재 활동이 있다면 라이브러리를 열어도 실행 대상을 바꾸지 않는다. 한 번에 한 블록만 실행하고 타이머 종료는 과제 완료가 아니다. 바로 시작을 막지 않으며 목표 행동을 하지 않았다면 실제 수행으로 집계하지 않는다.

## 2. 직무 목록과 행동 연결

직무 목록의 원본은 결과지의 공식 직무 ID·명칭·순서·출처·버전이다. TOP5를 재계산하거나 라벨 유사도로 임의 매핑하지 않는다. 별도 직무 목록을 수기로 만들어 공식 목록인 것처럼 쓰지 않는다.

`OfficialJobBinding`은 원본 직무 ID + sourceVersion + 공용 context ID + 검토된 behavior IDs를 연결한다. 지금 저장한 6개 맥락은 대표 설계 분류이며 공식 직무 코드가 아니다. `officialJobRefs`는 검증 전 빈 배열로 유지한다. 전체 공식 직종·직무군의 매핑 완료를 주장하지 않는다.

개발자는 공식 목록을 읽기 전용으로 가져와 모든 항목을 `unmapped / draft / reviewed / retired`로 집계한다. 미연결 항목에는 일반 행동 연습이나 직접 작성 경로를 제공하고 직무 전용 훈련처럼 표시하지 않는다. 성인은 TOP5·직접 선택·미정, 청소년은 공식 진로 후보·직접 선택·미정을 지원한다. 기존 career-review의 adult 계약을 teen으로 조용히 확장하지 않고 청소년 adapter를 별도로 검증한다.

6개 행동은 순서, 대안, 확인, 비교, 전달, 복귀다. 이것은 직무 행동 분류이지 PASS 4영역의 1:1 대체물이 아니다. 직무 적합성·채용 확률·인지능력 향상 산식을 만들지 않는다.

## 3. 개인화와 연령

기존 `routeFor/resolveTraining`의 공식 지원 순서와 강점 도움을 재사용한다. 결과지 단위·공식 등급·81유형·ID를 보존한다. 복수 약점 순서가 없거나 결과가 불일치하면 임의 판단하지 않고 일반 도움으로 전환한다.

- 계획 보완: 범위·예상 시간·순서 검토, 변경 또는 명시적 확정.
- 주의 보완: 현재 행동 선택; 생각 보관·깃발·복귀는 발생했을 때만 기록.
- 동시처리 보완: 실제 항목 2개 이상과 관계 확인.
- 순차처리 보완: 실제 단계 2개 이상, 직접 진행 표시.
- 통합: 기존 계획 → 실행 → 조정 흐름.

직무카드의 답변은 자동으로 PASS 행동 증거가 되지 않는다. 실제 UI 조작을 기존 증거 계약에 연결하고 카드·회차·practice ID로 중복 집계를 막는다. 과제 완료, 실행 종료, 목표 행동 수행, 자기보고, 외부 확인은 별개다.

강점 도움은 전체 지도·현재/다음 단계·목표/완료 기준·핵심 강조로 제공한다. 답을 대신 정하거나 81종 화면을 별도 제작하지 않는다. 사용자는 도움을 변경할 수 있고 변경 이력을 남긴다.

| 연령 | 입력·범위 설계 | 초기 제공 범위 |
|---|---|---|
| 중학생 | 실제 학습·준비 과제, 짧은 선택과 이유, 확인 질문 1개부터 | 일상카드 6개 후보 |
| 고등학생 | 수행평가·팀 활동, 대안 비교·우선순위·중간 마감 | 일상 6개 + 직무 모의 6개 후보 |
| 대학생·성인 | 프로젝트·생활·업무 맥락, 담당 역할·대기·인계, 자발적 서술 | 일상 6개 + 직무 모의 6개 후보 |

위는 구현할 연령 adapter 계약이다. 이번 데이터의 audience 태그만으로 연령별 UI 구현·QA 완료라 하지 않는다. 초등은 후속 별도 설계다.

## 4. 공통 저장과 개인 저장

공용: 검토된 상황 템플릿, 행동 분류, 공식 직무 매핑, 버전, 언어 리소스, 출처·검토 이력.
개인: 카드 인스턴스, 수정 이력, 검사 참조, 실제 실행, 메모, 로드맵 경험.
둘은 DB 컬렉션/접근권한을 분리한다. 공용 템플릿 JSON에 이름·연락처·사용자 ID·검사 원문·개인 수행 원문을 넣지 않는다.

- GitHub 규칙 위치: `docs/programs/nuvia-planner/`.
- 앱은 adapter로 공통 라이브러리를 읽는다. 운영 endpoint는 아직 지정하지 않는다.
- 사용자 데이터는 인증된 private 저장소에 저장하며 공개 GitHub나 공용 캐시에 저장하지 않는다.
- 관리자에게는 원본 수·직무 연결 수·언어 준비 수·실행 인스턴스 수를 분리해 보여준다.
- 개인별 번역·도움·시간 변경은 새 공용 원본이 아니라 private instance revision이다.
- 새 원본 ID는 실질적으로 다른 상황·결정 과제가 있고 중복 검토를 통과한 경우에만 발급한다.

## 5. AI 호출과 공용 편입

조회 → 기존 카드 또는 일반 행동 → 필요할 때 사용자가 AI 제안 요청 → 초안 미리보기 → 개인 저장 순서다. 과제 클릭, 매 타이머 tick, 재실행, 월간 리포트 생성에 자동 AI 호출을 붙이지 않는다. 사용자가 직접 만든 상황도 같은 개인 카드 경로로 저장한다.

서버에서 인증·허용량·비용 한도·중복 요청 토큰·입력 길이·출력 schema를 검사한다. 지출 한도는 운영자가 정하고 미설정 시 생성 비활성화한다. API 키는 클라이언트에 두지 않는다. 오류·할당량 초과 시 기존 카드와 직접 작성은 계속 사용할 수 있어야 한다. 모델에 개인 메모 전체나 검사 원문을 보내지 않고 사용자가 확인한 최소 맥락만 보낸다.

AI 출력은 실행 명령이 아닌 불신 데이터다. HTML/스크립트·외부 명령을 실행하지 않는다. 운영 로그는 개인 서술 원문을 기본 수집하지 않는다. 모델명·promptVersion·요청량·오류는 내부 메타데이터로 남긴다. 개인 캐시와 공유 캐시는 분리하며 개인 프롬프트/답변을 공유 캐시 키나 본문에 넣지 않는다.

공용 편입: 명시적 공유 동의 → 익명 템플릿 후보 생성 → 권리·개인정보·중복 확인 → 내용/연령/안전 검토 → 언어별 검수 → 승인된 immutable 버전 배포. 많이 사용됐다는 사실만으로 승인하지 않는다.

동의를 철회하면 대기 후보와 연결을 제거하고, 이미 배포된 카드의 권리 문제는 관리자 철회 절차로 처리한다. 익명화·공용 배포 후 모든 복사본을 회수할 수 있다고 약속하지 않는다. 개인정보 없는 새 일반 예시를 편집자가 작성하는 경로도 분리한다.

## 6. 전문·안전 직무 제한

항공보안 예시는 정보 확인과 의사소통에 한정한다. 반입 가능/불가 품목, 검색 기준, 현장 처리 순서를 AI가 창작하지 않는다. 현재 카드에 공식 절차의 정답은 없다. 전문 규정이 필요한 카드는 관할·공식 출처 URL·문서 버전·적용일·검토자·재검토일을 확보한 후에만 배포한다.

`draft → in-review → approved → retired`로 관리한다. 안전 민감 카드에는 승인된 출처와 재검토 기한이 없거나 만료됐으면 제공을 막는다. 기존 수행 이력은 원래 카드 버전 snapshot으로 보존하며 신규 시작만 중단한다. 이 패키지는 직무자격·현장교육을 대체하지 않는다.

## 7. 로드맵과 자소서 연동

카드 출처(`daily / job-simulation`)와 경험 맥락(`real-life / simulation`)을 분리 저장한다. 일상카드도 실제 행동을 하지 않았다면 실경험이 아니다. 사용자 확인은 외부 검증과 다르다.

카드 버전 → 개인 과제 revision → run → evidence → 사용자 확인 경험으로 연결한다. 처음 계획과 수정 이력을 남긴다. 완료 버튼 하나로 성과·강점·경험을 확정하지 않는다. 모의카드에 답했다고 현장 근무 경험으로 변환하지 않는다.

자소서 전달: 사용자가 경험과 허용 필드를 선택 → 선택 원문 미리보기 → 확인 버전 저장 → 인증된 수신자에게 전달. context/difficulty/action/adjustment/result/learning의 값과 출처를 유지한다. 사용자 점수·81유형·메모 전체는 기본 전송하지 않는다. 수정/철회/보고서 변경 시 재확인, 중복 수신은 같은 idempotency key로 한 번만 처리한다.

별도 확인된 AI 자소서 v3 설계에는 질문형 코치만 허용하고 자동 완성문은 금지되어 있다. 이 패치는 자소서 생성기를 만들거나 그 계약을 덮어쓰지 않는다. 경험 전달까지만 정의하고 문장 자동작성 허용 여부는 수신 제품의 승인된 계약을 따른다.

## 8. 월간 수행과 다음 계획

일상/모의 활동을 나누어 실제 수행한 행동·도움·수정을 보여준다. 합의한 연습의 고유 수행 수 / 합의 수를 기준으로 기존 월간 수행률 계산을 재사용한다. 새 카드 추가로 분모를 소급 변경하거나 시도를 여러 번 했다고 분자를 늘리지 않는다. 분모 0/기록 부족은 별도이며 0% 실패로 처리하지 않는다.

표시 구간은 사용자 확정대로 100%, 70% 이상 100% 미만, 50% 이상 70% 미만, 0% 이상 50% 미만이다. 소수 비율도 공백 없이 처리한다. 낮은 수행률은 능력 저하가 아니다. 일정·난이도·도움의 적합성을 확인하고 짧은 분량/적은 단계/강점 도움을 다음 달 초안으로 제안한다. 자동 강제 변경하지 않고 사용자가 확정한다.

## 9. 다국어와 UI 적용 조건

15개 언어: ko, en, ja, zh-CN, zh-TW, mn, th, vi, ar, ru, km, es, fr, it, az. 템플릿 문자열은 locale key로 분리한다. 이번에는 한국어 설계 원문만 작성했고 나머지 14개는 needs-review, resource 미작성이다. 어떤 언어도 release로 표시하지 않는다.

기존 UI key는 통합 시 재검색·재사용하고 기존 번역을 덮어쓰지 않는다. 제품 예시도 번역 대상이며 사용자 원문은 자동 번역하지 않는다. 선택 언어의 검수된 카드만 추천한다. 번역 누락 때문에 다른 언어 카드로 몰래 대체하지 않는다.

첫 화면/주요 화면 오른쪽 상단 선택기, 상태 보존 전환, 44px 버튼, RTL, 360/768/1440px·인쇄 검수를 통과한 후 출시한다. 현재 작업대 2.5D 디자인을 유지하고 입력 완료 전 자동 실행하지 않는다. 사용자 화면에는 실제/모의 구분과 안전 안내를 보여주되 sourceHash·draft·QA 상태는 내부 관리자에만 둔다.

## 10. 개발 순서와 승인

1. 공식 직무 목록·원본 ID/버전 확인, 매핑 대장 작성.
2. 대표 카드 내용 검토와 개인화/연령 UI 설계.
3. 공용 읽기 adapter + private instance 생성 연결. 기존 Card/Run 저장 계약 마이그레이션은 명시적 버전으로.
4. 실제 활동/모의 활동 → roadmap 선택 전달 계약 검증.
5. 15개 locale + 기능/권한/회귀 QA.
6. 조회 중심으로 먼저 출시; AI 생성과 관리자 편입은 인증·예산·검토 경로를 갖춘 뒤 추가.

현재 범위는 1의 연결 구조, 2의 콘텐츠 초안, 3~6의 구현 계약이다. 실제 전체 직무 매핑, 앱 통합, 운영 서버, 외부 API 호출, 다국어 완역, 브라우저 QA는 수행하지 않았다. 기존 제품/main/공개 URL은 변경하지 않는다.
