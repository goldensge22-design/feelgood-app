# 긴 대기 자동 수신·복구 보강 — 2026-11-15

## 바뀐 흐름

최신 작성 화면은 POST `/api/career/ai-jobs`로 짧게 접수(202)하고 GET `/api/career/ai-jobs/:id`로 자동 조회한다. 정상 `queued`/`running`에는 전체 HTTP 200초·대기 180초 실패를 적용하지 않는다. 브라우저는 15초짜리 개별 HTTP 제한과 2~15초 연결 재시도만 사용하며, 접수 후에는 새 생성 POST 없이 GET으로 기다린다. 서버는 기존 동시 4개·2초 시작 간격·최대 1회 일시적 rate 재시도·공유 1,100회/고정 5시간·계정 30회/5시간 및 8회/분을 유지한다. 모델·품질·출력 토큰 상한은 변경하지 않는다. 한 번의 공급자 처리 제한 45초는 그대로다. 즉, 정상 큐 대기 시간과 전송 뒤 공급자 시간초과를 구분한다.

이전 `/ai-assist`는 호환용 동기 경로로 남아 있지만 새 작성 화면에서는 사용하지 않는다. 모든 복제본에서 새 경로로 업데이트해야 한다. 서로 다른 서버를 위한 분산 한도를 늘리거나 프로세스별로 따로 허용하지 않는다.

## 복구와 개인정보

- 계정·지원서별 브라우저 복구 포인터에 무작위 client nonce, opaque job ID, 맥락 SHA256, 기존 소스 지문, 작업 종류/선택 경험 ID·작성 언어/목적만 저장한다. 학생 원문·키·세션·선택 자료 복사본은 포인터에 넣지 않는다. 기존 학생 작성 저장소는 그대로 둔다.
- 처음 POST하기 **전** 포인터를 저장하며 저장이 실패하면 생성 요청 자체를 보내지 않는다. POST 응답을 놓쳤어도 GET `/ai-jobs/by-client/:clientId`로 인증된 본인 요청을 찾는다. 같은 nonce·같은 선택 내용의 초기 POST 재전송은 같은 공유 원장을 사용한다.
- 새로고침/연결 복구 시 포인터와 현재 맥락이 일치할 때만 같은 요청을 자동 조회한다. 지원서·경험·본문·원본 버전·문항이 바뀌면 이전 결과를 적용하지 않는다. UI 언어만 바뀌는 것은 원본 내용 변경이 아니며 학생 글을 번역하지 않는다.
- 서버는 **동의한 목적별 최소 선택 입력**을 기존 계정/요청 결합 AES-GCM으로 암호화해 큐에 보관한다. 전송 쿠키·사용자 원래 ID·미선택 메모·전체 검사 원문을 추가하지 않는다. 결과는 기존과 같이 5시간 계정별 암호화 재사용한다.
- 선택 입력은 완료·취소·재시도 불가능한 실패·과금 불명 상태 확인 시 지운다. 대기 복구 입력의 사용 기한은 5시간이며 다음 워커 접근에서 만료 정리한다. 서비스가 완전히 중단되어 있으면 정리도 실행되지 않으므로 실제 보존/삭제 정책은 운영자가 확인해야 한다. 중복 방지 메타 원장은 자동 삭제하지 않는다.
- 원래 서버 연결이 끊겨도 다른 복제본이 암호화된 **미전송 대기**를 처리한다. 이미 전송 예약된 작업은 재획득하지 않는다. 서버 단절로 90초 후 과금 여부가 불명이면 `uncertain`으로 끝내며 자동 새 생성하지 않는다.
- 사용자의 취소는 대기 작업을 취소한다. 이미 전송된 작업은 처리·과금될 수 있으며 결과가 나중에 도착해도 취소한 화면에 삽입하지 않는다.
- 실제 계정/원본/기업 공유·내보내기 범위는 변경하지 않는다. 모델 후보가 자동으로 본문에 들어가지 않는다.

## 운영 적용

새 외부 서비스나 DB 테이블은 추가하지 않았다. 직전 공유 조정 패키지의 PostgreSQL 테이블 3개 JSON 상태를 확장한다. 동일 DB·동일 32자 이상 SESSION_SECRET·동일 조정 정책을 모든 복제본에 유지한다. 비밀키를 교체하거나 설정이 없을 때 메모리 큐로 우회하지 않는다. 포인터의 사용자 ID만으로 서버 접근을 허용하지 않으며 Clerk 인증 ID로 매번 소유권을 검사한다.

대기 자료는 원래 접수한 공급자·모델·응답 형식과 결합된다. 다르게 설정된 복제본은 해당 자료를 다른 모델/관리형 연결로 처리하지 않는다. 운영자는 모든 복제본의 설정 일치를 확인해야 한다. 한 복제본을 BYOK, 다른 복제본을 관리형으로 섞어 쓰지 않는다.

워커는 첫 접수/인증된 상태 조회 시 시작하고, 처리할 합성/실제 자료가 없는 경우 AI를 호출하지 않는다. 서버를 안전하게 종료할 때는 그 프로세스가 다른 계정 요청을 처리 중일 수도 있음을 고려해야 한다. 이번 부하검사 초기의 조기 워커 종료 실패는 검사기가 자기 클라이언트 묶음만 끝났다고 DB 풀을 닫았기 때문이다. 최종 검사기는 공유 코호트 전체가 끝날 때까지 워커를 유지한다. 실제 급작스러운 프로세스 종료는 `uncertain` 보호로 남기는 것이 의도된 안전 동작이다.
